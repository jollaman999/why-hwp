# refcompare

[English](README.md)

변환기 출력이 한글(Hwp)과 얼마나 같은지 재는 개발용 도구다. `why-hwp` 실행 파일에는 들어가지 않는다.

- `ref` 는 원격 Windows PC 의 한글로 기준 출력을 만든다.
- `cmp` 는 후보 출력(어느 변환기가 만들었든)을 기준과 비교해 표를 낸다.

## 필요한 것

| 어디 | 무엇 |
|------|------|
| 원격 Windows PC | 한글 (Hwp 2024 로 확인), Windows 실행이 켜진 WSL (`/proc/sys/fs/binfmt_misc/WSLInterop`), WSL 안의 ssh 서버 |
| 이 PC | Go, 원격에 키로 로그인되는 `ssh`·`scp` (`BatchMode=yes` 라 비밀번호를 묻지 않는다), poppler-utils 의 `pdftotext`·`pdffonts`·`pdftoppm` |
| 이 PC (선택) | MuPDF 의 `mutool` (1.27 로 확인). Type 3 글꼴이 든 문서에서만 쓴다 (아래 참고) |

원격은 환경 변수로만 받는다.

| 변수 | 뜻 |
|------|----|
| `WHY_HWP_REF_HOST` | ssh 대상. 예: `user@host` |
| `WHY_HWP_REF_DIR` | Windows 에서도 보이는 `/mnt/<드라이브>/` 아래 WSL 폴더. 예: `/mnt/c/Users/<나>/why-hwp-ref`. 도구는 `<dir>/refcompare` 안에서만 일하고 그 밖은 건드리지 않는다 |

## ref: 기준 만들기

```sh
go build -o /tmp/refcompare ./tools/refcompare
WHY_HWP_REF_HOST=user@host WHY_HWP_REF_DIR=/mnt/c/Users/me/why-hwp-ref \
  /tmp/refcompare ref -corpus CORPUS -out OUT
```

- `CORPUS` 는 `.hwp`·`.hwpx` 파일이 든 폴더다 (하위 폴더는 읽지 않는다).
- `<name>`(확장자까지 포함한 파일 이름)마다 한글로 `OUT/ref/<name>.pdf`, `<name>.txt`, 그리고
  다른 형식(hwp 입력이면 `<name>.hwpx`, hwpx 입력이면 `<name>.hwp`)을 만든다.
- 변환은 Windows 용으로 빌드한 `why-hwp convert -engine hancom`(한글 COM)이다. 기본값은 지금 폴더의 모듈을
  커밋 안 된 변경까지 포함해 빌드한다. 커밋된 상태로 하려면 직접 빌드해 `-exe` 로 넘긴다:
  `git archive HEAD | tar -x -C /tmp/w && (cd /tmp/w && GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -o why-hwp.exe ./cmd/why-hwp)`.
- 실행 파일은 원격 사본과 SHA-256 이 다를 때만 복사한다. 입력은 해시로 만든 이름으로 복사하므로
  파일 이름이 원격 셸에 닿지 않는다.
- `OUT/ref/manifest.json` 에 출력마다 입력 해시를 적는다. 같은 입력으로 만든 출력이 있으면
  다시 만들지 않는다. `-force` 는 전부 다시 만든다.
- ssh 호출은 모두 `-n`, `BatchMode=yes` 이고 시간 제한이 있다. `-timeout`(기본 120s)은 변환 한 번에
  주는 한글의 제한 시간이다.
- 한글이 빈 텍스트 파일을 저장하면(차트만 있는 문서처럼 글자가 없는 문서) 기준 `.txt` 를 빈 파일로 둔다.
- 인쇄 설정이 두 쪽 모아 찍기인 문서는 `OUT/ref/<name>.oneup.pdf` 도 만든다. 같은 문서를 한 장에
  한 쪽으로 인쇄한 것이다 (*한 장에 한 쪽 기준* 절). 설정은 문서의 HWPX 형태에 든 `settings.xml` 의
  `PrintMethod` 가 4인 것으로 안다. HWPX 형태는 hwpx 입력이면 입력 자체, hwp 입력이면
  `OUT/ref/<name>.hwpx` 다. `ref` 는 그 파일에서 이 값 하나만 0 으로 바꾼 사본을 만들어(다른 zip 항목은
  저장된 그대로, 같은 순서로 복사한다) 한글로 인쇄한다. 사본은 남기지 않고, PDF 는 다른 출력처럼
  캐시한다.

## 후보

`cmp` 는 후보를 만들지 않는다. `<name>.pdf`, `<name>.txt`, 그리고 `<name>.hwpx`(hwp 입력) 또는
`<name>.hwp`(hwpx 입력)가 든 폴더를 읽는다. 없는 파일은 표에 적고 만들지 않는다.

rhwp 명령줄 도구(rhwp 저장소에서 빌드)로는 이렇게 만든다.

```sh
for f in CORPUS/*.hwp CORPUS/*.hwpx; do
  n=$(basename "$f")
  rhwp export-pdf "$f" -o "CAND/$n.pdf"
  rm -rf /tmp/txt && rhwp export-text "$f" -o /tmp/txt && cat /tmp/txt/*.txt > "CAND/$n.txt"
  case "$n" in
    *.hwp)  rhwp export-hwpx "$f" "CAND/$n.hwpx" ;;
    *.hwpx) rhwp convert "$f" "CAND/$n.hwp" ;;
  esac
done
```

`export-text` 는 쪽마다 파일 하나(`<base>_001.txt`, ...)를 쓴다. 이름 순서로 이어 붙인다.

## cmp: 비교

```sh
/tmp/refcompare cmp -out OUT -cand CAND [-tol 1.0] [-fit scale] [-skip-memo] [-ink 1.0] [-ink-all] [-reconvert]
```

표는 stdout 과 `OUT/report.md` 에 나온다. 종료 코드는 모든 문서가 통과하면 0, 하나라도 실패하거나
비교하지 못하면 1, 사용법이 틀리면 2 다.

| 옵션 | 뜻 |
|------|----|
| `-tol` | 허용하는 낱말 가장자리 최대 편차 (pt, 기본 1.0) |
| `-fit` | 재기 전에 기준 쪽을 후보 쪽에 맞추는 방법: `scale`(같은 비율 축척 + 이동, 기본), `shift`(이동만), `none` |
| `-skip-memo` | 한글의 메모 영역에 있는 기준 낱말을 뺀다 (아래 참고) |
| `-ink` | 그림으로 판정하는 쪽과, 기준의 그림에서 찾아보는 낱말에 허용하는 그림 차이의 최대값 (%, 기본 1.0, *그림으로 판정하는 쪽*·*기준이 그림으로 그린 글자* 참고) |
| `-ink-all` | 나머지 쪽도 그림 차이를 재서 `## Picture difference of every page` 에 적는다. 판정은 바뀌지 않는다 |
| `-reconvert` | 후보 HWP/HWPX 를 원격 한글로 PDF 로 인쇄해(`OUT/reconv/`, `ref` 처럼 캐시) 기준 PDF 와도 비교한다. `ref` 와 같은 환경 변수가 필요하다. `-exe`·`-force`·`-timeout` 은 `ref` 와 같다 |

### PDF 비교 방법

1. `pdftotext -bbox` 로 낱말과 그 상자를 얻는다.
2. 낱말을 읽는 순서(쪽, 위에서부터 줄, 왼쪽부터)로 놓는다. 두 PDF 는 글자를 쓰는 순서가 달라서
   내용 스트림 순서는 쓰지 않는다.
3. 쪽마다 `-fit` 의 맞춤을 먼저 한 번 구한다. 낱말을 짝짓는 데만 쓴다. 기준 쪽에 한 번, 후보 쪽에
   한 번만 나오는 글자의 낱말로 구한다. 이런 낱말은 반복 때문에 엉뚱하게 짝지어질 수 없다. 그런
   낱말이 3개보다 적은 쪽은 읽는 순서로 짝지은 낱말(4의 넷째 단계)로 구한다.
4. 낱말을 일대일로 짝짓는다. 아래 단계마다 앞 단계에서 짝을 못 찾은 낱말만 다루고, 앞의 네 단계는
   같은 쪽 번호 안에서만 짝짓는다.
   1. 같은 자리의 같은 글자. 가까운 것부터 짝짓는다. 먼저 구한 맞춤으로 옮긴 뒤 두 낱말 상자가
      가로로 겹치고, 세로 위치의 차이가 높이가 낮은 쪽 상자의 높이 절반보다 작으면 같은 자리다.
   2. 같은 자리의 다른 글자. 한 낱말을 서로 다르게 쪼갠 경우(`온·오` 와 `온·` + `오`)다. 겹치는
      낱말들을 글자 단위로 짝짓는데, 짧은 쪽의 글자가 모두 짝지어지고 짧은 쪽이 긴 쪽 길이의 절반
      이상일 때만 한다. `7)` 위에 놓인 `5)` 는 짝짓지 않는다. 겹치는 낱말들은 읽는 순서로 늘어놓고,
      그렇게 해서 한 낱말이 안 되면 왼쪽부터 늘어놓는다. 상자가 높은 Type 3 글꼴의 낱말(*Type 3
      글꼴* 절)은 상자 가운데가 두 줄 사이에 있어서 윗줄로 읽히고, 그러면 자기가 끼어 있는
      낱말들보다 앞에 온다 (`가나」다` 에 대해 `가나` + `」` + `다` 인데 `」` 가 `가나` 보다 먼저 읽힌다).
   3. 쪽 안 어디든 같은 글자. 거리의 합이 가장 작게 짝짓는다. 자리를 옮긴 낱말이 여기서 짝지어지고,
      옮겨 간 제 자리까지의 거리를 잰다.
   4. 읽는 순서. 같은 낱말을 순서대로 짝짓고(최장 공통 부분열), 짝지은 두 낱말 사이에 남은 글자는
      글자 단위로 다시 짝짓는다. 문서 전체에 대해 구한 뒤 두 글자가 모두 아직 짝이 없는 것만
      받는다. 쪼개진 데다 자리도 옮긴 낱말이 여기서 짝지어진다.
   5. 그래도 양쪽에 남은 같은 글자의 낱말은 쪽을 가리지 않고 가장 가까운 것끼리 짝짓는다. 다른
      쪽으로 넘어간 낱말이다.

   읽는 순서만으로는 모자라다. 반복되는 낱말(표 칸 수백 개의 `-`, 수식의 `x`)은 상대 PDF 의 순서에서
   다음에 오는 것과 짝지어지는데, 줄이 다르게 묶이거나 표 칸이 다르게 섞이는 곳에서는 두 PDF 의
   순서가 다르다. 그런 짝은 서로 다른 두 낱말 사이의 거리를 잰다. 낱말 가장자리가 모두 1.5pt 안에
   있는 수식에서 20pt, 그림 차이가 0.07% 인 쪽에서 169pt 가 나왔다. 읽는 순서만으로 짝지었을 때와 다른
   낱말과 짝지어진 기준 낱말의 수가 보고서에 나온다(`out of reading order`).

   자리를 옮긴 낱말이 같은 글자의 다른 낱말 뒤에 숨지는 못한다. 그 낱말에는 제 짝이 있기 때문이다.
   여러 줄이 통째로, 같은 글자의 두 낱말 사이 거리만큼 옮겨 가면 한 낱말이 제 자리에 와 앉은 다른
   낱말과 짝지어질 수 있다. 그때는 옮겨 간 줄들의 끝에 남은 낱말이 멀리 있는 것과 짝지어져서 문서는
   그대로 실패하고, 가장 큰 편차는 처음 옮겨진 낱말이 아닌 다른 낱말에서 나온다.
5. 같은 자리의 다른 글자가 짧게(2자까지) 이어질 때, 기준 글자가 기호 글꼴 코드(사용자 정의 영역,
   또는 Wingdings 글머리표의 `Ÿ` 같은 코드 페이지 1252 바이트)이고 후보 글자가 문자·숫자가 아니면
   *치환*으로 본다. 문자나 숫자가 바뀐 것은 치환이 아니다.
6. 두 PDF 가 같은 글자에서 낱말 경계를 가질 때만 가장자리를 잰다. 짝지은 글자로 시작하는 낱말의
   왼쪽 가장자리, 짝지은 글자로 끝나는 낱말의 오른쪽 가장자리다. 가장자리 점은 (x, 낱말 상자의
   세로 가운데)이고, *Type 3 글꼴* 절에 적은 낱말은 (x, 기준선)이다.
7. 쪽 쌍마다 짝의 가장자리로 `-fit` 의 맞춤을 구한다(4의 다섯째 단계의 짝은 뺀다. 최소제곱으로
   구하고, 그 결과에서 멀리 떨어진 점을 빼고 한 번 더 구한다). 가장자리가 6개보다 적은 쪽은 이동만
   맞춘다. 한글은 메모 말풍선 자리를 내려고 본문을 줄이므로 축척이 필요하다.
8. 가장자리 편차는 7의 맞춤으로 맞춘 뒤 가로·세로 거리 중 큰 값이다 (후보 pt).

`-skip-memo` 를 주면, 짝이 없는 기준 낱말 가운데 그 쪽이 줄어들었고(맞춤 축척 1.01 초과) 맞춘 뒤
그 쪽의 모든 후보 낱말보다 오른쪽에 놓이는 것을 뺀다. 한글이 메모를 찍는 자리다.

### 모아 찍기 (한 장에 두 쪽)

한글은 문서의 인쇄 설정을 따르고, 그중에는 가로 용지 한 장에 두 쪽을 나란히 찍는 설정이 있다.
두 PDF 가 쪽을 같은 비율로 줄였으면 장 하나에 맞춤 하나로 두 쪽이 다 맞고 더 할 일이 없다.
비율이 다르면 쪽마다 자기 반쪽의 모서리를 기준으로 줄어든 것이라 맞춤 하나로는 두 반쪽이 같이
맞지 않는다. 한글은 메모 말풍선 자리를 내려고 쪽을 한 번 더 줄인다. 20장짜리 문서 하나에서 후보의
쪽이 기준의 1.29배였고, 두 반쪽에 필요한 맞춤이 122pt 떨어져 있어서, 장 단위로 비교하면 편차
609pt 에 다른 쪽으로 간 낱말 88개로 나왔다.

이런 문서는 반쪽 단위로 비교한다. 장마다 왼쪽 반과 오른쪽 반이 각각 한 쪽이다. 읽는 순서,
`-fit` 의 맞춤(다른 쪽에 쓰는 것과 같은 종류), 그림 판정을 반쪽마다 따로 하고, 다른 반쪽으로 간
낱말은 다른 쪽으로 간 낱말(`moved`)이다.

아래를 모두 만족하는 문서만 이렇게 비교한다.

1. 두 PDF 의 모든 쪽이 가로다.
2. 두 PDF 모두 쪽의 가운데 세로선에 걸친 낱말이 없고, 선의 양쪽에 낱말이 있다.
3. 반쪽마다 축척과 이동을 맞췄을 때, 두 반쪽 모두 축척이 나온(가장자리 6개 이상) 장의 절반이
   넘는 장에서 두 맞춤이
   - 두 반쪽의 왼쪽 위 모서리를 후보 장 폭의 반만큼 떨어뜨려 놓는다 (2pt 안에서). 모아 찍기는
     쪽을 얼마로 줄이든 이렇게 놓는다.
   - 그 거리가, 두 축척의 평균으로 장 전체를 맞춤 하나로 맞췄을 때의 거리와 4pt 넘게 다르다
     (4pt 는 A4 장 폭 반의 1% 로, 메모 축소로 보는 비율과 같다).

3의 두 거리는 축척이 1이면 같다. 그래서 둘 다 성립하는 것은 반쪽이 줄거나 늘었는데 모서리는
제자리에 있을 때뿐이다. 그 밖의 문서는 전과 같이 한 장을 한 쪽으로 비교하고, 그쪽이 더 엄격하다.

- 2단으로 짠 가로 쪽에서 후보가 오른쪽 단을 옮겨 놓으면(5pt 든 80pt 든) 두 반쪽의 축척이 1이다.
  전처럼 실패한다.
- 한글이 통째로 줄인 가로 쪽은 맞춤 하나로 맞는다.
- 두 PDF 가 쪽을 같은 비율로 줄인 모아 찍기 문서도 장 하나에 맞춤 하나로 맞는다. 이때 다른
  반쪽으로 간 낱말은 `moved` 가 아니라 수백 pt 의 편차로 나온다.

위 문서에서는 20장 중 19장이 3을 만족했다 (모서리 거리는 장 폭 반에서 0.4~0.8pt, 맞춤 하나일
때의 거리에서 122~123pt). 나머지 한 장은 왼쪽 반에 낱말이 셋뿐이고 모서리 거리가 2.8pt 어긋난다.

보고서에서 이런 문서는 `scale` 칸에 `two-up: left <축척>, right <축척>` 이 나오고, `pages` 는 장
수이며, 쪽은 장 번호와 반쪽으로 적는다. `p8L` 은 8장의 왼쪽 반이다. 한 장의 두 반쪽은 같은 문서의
두 쪽이라 축척이 같아야 한다. 0.5% 넘게 다르면(모아 찍기가 아닌 문서들의 쪽 사이 차이는 0.33%
까지였다) 그 칸에 `halves differ on sheets ...` 가 붙고, `## Differences` 에 두 축척과 각각을 구한
가장자리 수가 나온다. 다른 맞춤 축척과 같이 보여만 주고 판정에는 넣지 않는다.

반쪽의 그림 판정은 장을 그린 뒤 다른 반쪽을 흰색으로 덮고 한다.

한 장에 한 쪽 기준이 있는 문서는 이렇게 비교하지 않는다 (다음 절). `-reconvert` 의 왕복만 예외다.

### 한 장에 한 쪽 기준

한글의 모아 찍기 인쇄에는 문서가 다 들어 있지 않을 때가 있다. 위의 20장짜리 문서에서 한글 PDF 에는
표 칸 885개가 없다. 열 쪽에서 넓은 표의 오른쪽 열이 장의 오른쪽 반에서 잘린다. 그 쪽들을 온전히 그린
후보는 짝 없는 낱말이 885개 나와서, 맞게 그려도 통과할 수 없다. 같은 문서를 한 장에 한 쪽으로
인쇄하면 40쪽이고 칸이 다 있다.

그래서 `OUT/ref/<name>.oneup.pdf` 가 있고 (*ref* 절) `manifest.json` 에 `<name>.pdf` 와 같은 입력으로
적혀 있으면, 후보 PDF 를 그것과 비교한다.

- 후보가 모아 찍은 장이면 (모든 쪽이 가로이고, 쪽의 가운데 세로선에 걸친 낱말이 없고, 선의 양쪽에
  낱말이 있다) 반쪽으로 나눈다. *n* 번째 반쪽을 한 장에 한 쪽 기준의 *n* 쪽과, 두 쪽을 비교할 때와
  똑같이 비교한다. 짝짓기, 쪽마다의 `-fit` 맞춤, 후보 pt 로 잰 편차, 그려진 글자가 모두 같다. 후보가
  한 장에 두 쪽을 넣으려고 쪽을 줄인 비율(위 문서에서 0.7085~0.7103)과 한글이 메모 때문에 기준
  쪽을 줄인 비율은 맞춤이 흡수한다. 기준의 쪽 수가 후보의 반쪽 수보다 하나 적고 마지막 반쪽에
  낱말이 없으면 그 반쪽은 쪽으로 치지 않는다. 그 장을 그려 보고, 반쪽에 잉크가 있으면 문서는
  실패한다.
- 그 밖의 후보는 한 장에 한 쪽 기준과 쪽 대 쪽으로 비교한다.
- 모아 찍기 기준 `<name>.pdf` 로는 장만 본다. 후보의 장 수가 같아야 하고, 장마다 가로·세로가
  `-tol` pt 안에서 같아야 한다. 인쇄 설정을 따르지 않은 후보는 낱말이 모두 제자리에 있어도
  여기서 실패한다.

보고서에서 이런 문서는 쪽 수 뒤에 `one-up ref; sheets <기준>/<후보>` 가 붙는다. 쪽 수는 한 장에 한 쪽
기준의 쪽 수와 후보의 반쪽 수다. `scale` 칸에는 `halves: left <축척>, right <축척>` 이 나오고, 쪽은
문서의 쪽 번호로 적는다. `## Differences` 에 어느 기준을 왜 썼는지 적는다.

`-reconvert` 의 왕복은 전처럼 모아 찍기 기준과 비교한다. 그때는 두 PDF 모두 한글이 모아 찍은 것이라
같은 식으로 잘린다.

### Type 3 글꼴

한글은 일부 글꼴을 PDF 에 Type 3 글꼴로 넣는다. 이 글꼴에는 글자 위·아래 높이(ascent, descent)가
적혀 있지 않아서 `pdftotext` 가 짐작한 글꼴 크기로 낱말 상자를 지어낸다. 11pt 한 줄에서 상자 높이가
30pt 인 낱말과 7pt 인 낱말이 나왔다. 이런 상자의 세로 가운데는 글자가 있는 자리가 아니다. 좌우
가장자리는 맞다. 기준선이 1pt 안에서 같은 낱말들이 세로로 3.4~4.7pt 어긋난 것으로 나왔었다.

`pdffonts` 가 기준이나 후보 PDF 에서 Type 3 글꼴을 내면 두 PDF 에 `mutool draw -F stext` 를 돌린다.
글자마다 원점(기준선 위의 점)과 글꼴 이름이 나온다. 낱말의 기준선은 첫 글자의 것이다. 첫 글자는
낱말 상자의 왼쪽 가장자리에 있고 낱말의 첫 문자와 같은 글자다. Type 3 상자는 높아서 윗줄의 같은
문자까지 들어올 수 있다. 그래서 그런 글자가 하나뿐인 낱말들로 글꼴마다 기준선이 상자의 어느
높이에 있는지 먼저 알아내고, 나머지 낱말은 그 높이에 가장 가까운 글자를 고른다.

그 뒤 아래 두 가지 짝은 상자 가운데가 아니라 기준선으로 세로 위치를 잰다. 가로 위치와 맞춤은
다른 짝과 같다.

- 두 낱말 중 하나에 Type 3 글자가 들어 있다.
- 두 낱말의 글자 범위가 다르다. `pdftotext` 는 Type 3 글꼴이 시작하는 곳에서 낱말을 끊는다. 그래서
  기준에는 `(` 와 `abc` 가, 후보에는 `(abc` 가 나오고 두 상자는 서로 다른 글꼴에서 나온 것이 된다.

그 밖의 짝은 상자 가운데로 잰다. Type 3 글꼴이 없는 문서는 모든 짝이 그렇고 `mutool` 을 돌리지
않는다. 보고서의 `type 3` 칸에 기준선으로 잰 가장자리 수가 나온다.

`mutool` 이 없거나, `pdffonts` 가 낸 Type 3 글꼴의 글자가 `mutool` 출력에 없으면 Type 3 낱말도
상자 가운데로 재고 `type 3` 칸에 `box middle:` 과 이유를 적는다. 이런 문서에서는 실제로는 없는 세로
편차가 몇 pt 씩 나온다.

### 그림으로 판정하는 쪽

한글은 차트 글자를 외곽선으로 그려서 그 자리에 낱말이 없다. 기준 PDF 에 낱말이 하나도 없는
쪽(차트, 그림, 빈 쪽)은 *그림 쪽*이다. 이 쪽의 후보 낱말은 짝지을 수 없으므로 짝 없는 낱말로 세지
않고, 쪽을 그려서 판정한다. 후보에만 낱말이 없는 쪽은 그림 쪽이 아니다. 후보가 글자를 잃은 것이라
기준 낱말이 짝 없는 낱말로 남는다.

1. `pdftoppm` 으로 두 PDF 의 그 쪽을 1pt 에 4픽셀, 컬러로 그린다.
2. 그린 쪽의 *윤곽*은 색이 바뀌는 경계의 어두운 쪽 픽셀이다. 좌우·위아래로 2픽셀 안에, 색 채널
   하나가 64(255 중) 이상 다른 픽셀이 있으면 윤곽이다. 원 그래프의 두 조각은 밝기가 거의 같고
   색조만 다를 수 있어서 컬러로 본다.
3. 윤곽 픽셀에서 가로·세로로 `-tol` pt (낱말 가장자리와 같은 기준, 기본값에서 4픽셀) 안에 상대 쪽의
   윤곽 픽셀이 없으면 *짝 없는 윤곽*이다. 상대 쪽은 차이 32 이상이면 윤곽으로 쳐 준다. 경계 근처의
   값이 한쪽은 65, 다른 쪽은 63 이라서 짝이 없어지는 일을 막는다.
4. 그림 차이는 윤곽 가운데 짝 없는 윤곽의 비율이다. 두 쪽에서 각각 구해 큰 쪽을 쓴다. 둘 다 빈
   쪽이면 0, 한쪽에만 그려져 있으면 100% 다.
5. 그림 차이가 `-ink` % (기본 1) 이하면 통과다. 그림 쪽에는 짝지은 낱말이 없어서 맞춤도 없다.
   두 쪽을 그대로 비교한다.

이런 문서의 판정은 `pass (picture)`, `FAIL (picture)` 로 적고 `picture` 칸에 그림 쪽마다 그림 차이를
적는다. 낱말 비교로 통과한 것과 섞이지 않는다. 쪽을 그리지 못하면 그 문서는 실패다.

수치의 근거 (문서 18개, 한글이 쓴 글꼴로 만든 후보, `-ink-all`):

- 차이 64: `pdftoppm` 은 PDF 에 없는 것을 그리고 그것이 두 PDF 에서 다르다. 한글이 원 그래프 조각을
  나눠 그린 타일 사이의 이음매(차이 1), 가장자리가 투명한 그림 둘레의 흐린 선(차이 36, `mutool` 은
  안 그린다)이 그렇다. 한쪽은 JPEG, 다른 쪽은 무손실로 넣은 그림은 결도 다르다. 차이 32 로 재면 그림
  두 장이 제자리에 있는 쪽이 2.0% 로 나왔고 64 로 재면 0.0% 다.
- 문턱 1%: 낱말이 있고 낱말 비교를 통과한 47쪽 중 46쪽이 0.41% 이하(그중 45쪽은 0.1% 미만)였다.
  나머지 한 쪽은 기준에만 메모 말풍선이 있다(44%). 그림 쪽 둘은 0.39% 와 0.00% 였다. 열 쪽(그 둘과
  낱말 쪽 여덟)을 일부러 오른쪽이나 아래로 1.25pt 옮기면 1.2~24%, 2pt 옮기면 11~45% 가 나왔다.
  쪽 수가 다른 문서의 쪽은 57% 이상이었다.

이 값은 비율이지 최대값이 아니다. 글자가 가득한 쪽에서 낱말 몇 개가 1.8~3.5pt 어긋난 경우는
0.03~0.49% 로 문턱 아래다. 그래서 낱말이 있는 쪽은 그림이 아니라 낱말로만 판정한다.

### 기준이 그림으로 그린 글자

한글은 다른 낱말이 있는 쪽에서도 차트 글자를 외곽선으로 그리고, 문서에 그림으로 들어 있는 차트에는
글자가 아예 없다. 후보에는 그 자리에 낱말이 있고 짝이 없다. 이런 낱말은 기준이 보여 주는 것과 같은
것일 수도 있고, 후보가 없는 글자를 만들어 냈거나 엉뚱한 곳에 찍은 것일 수도 있다. 그래서 그냥 빼지
않는다. 기준 PDF 의 그림에서 찾아보고, 제자리에서 같은 모양을 찾은 낱말만 짝 없는 낱말에서 뺀다.

1. 짝 없는 후보 낱말마다 `pdftoppm` 으로 두 PDF 의 그 둘레를 1pt 에 8픽셀로 그린다. 기준은 그 쪽의
   맞춤(*PDF 비교 방법* 7단계)이 낱말 상자를 옮겨 놓는 자리를 그린다.
2. 윤곽은 *그림으로 판정하는 쪽* 2단계와 같다. 두 쪽에서 낱말 상자 안의 윤곽 픽셀을 모은다.
3. 기준은 가로·세로로 `-tol` pt 까지 옮겨 볼 수 있다 (낱말 가장자리와 같은 기준). 1픽셀씩, 작은
   이동부터 해 본다. 어떤 이동에서 두 쪽 모두 상자 안에 윤곽이 있고, 각 쪽 윤곽 가운데 0.25pt 안에
   상대 쪽 윤곽이 없는 픽셀이 `-ink` % 이하이면 두 모양이 *겹친다*고 한다.
4. 그런 이동 하나에서 겹치고, 거기서 왼쪽·오른쪽·위·아래로 `-tol` + 0.5pt 더 옮긴 네 자리에서는
   겹치지 않을 때 그 낱말을 *그려진 글자*로 본다. 네 자리에서도 겹치면 상자 안이 잉크로 가득 차서
   (방사형 차트의 한가운데, 빗금 친 영역) 어떤 모양이든 겹치는 것이라 그 낱말에 대해 알 수 있는
   것이 없다.
5. 같은 자리(짝짓기 4.1 단계의 기준)에 다른 낱말이 있으면 찾아보지 않는다. 다른 후보 낱말이거나
   짝 없는 기준 낱말이다. 그 자리의 잉크는 그 낱말의 것이기 때문이다. 그래서 낱말을 두 번 찍은
   후보에는 짝 없는 낱말이 그대로 남고, 기준과 다른 글자를 찍은 후보(기준 PDF 가 수식 글꼴의 코드로
   알려 주는 자리의 `O`)도 그렇다. 후보에만 있는 쪽의 낱말도 찾아보지 않고, 그림 쪽의 낱말은 그림
   판정에 맡긴다.

그려진 글자는 짝 없는 낱말로 세지 않는다. 보고서의 `drawn` 칸에 전체 개수와 쪽마다의 개수, 그리고
찾았을 때의 이동 가운데 가장 큰 값을 적는다 (모양 자체는 0.25pt 더 떨어져 있을 수 있다). 실패한
문서는 `## Differences` 에도 적고, `-ink-all` 의 쪽 표에도 `drawn` 칸이 있다.

짝 없는 낱말로 남는 것: 기준에 잉크가 없는 자리의 낱말, `-tol` 과 0.25pt 보다 멀리 있는 모양, 그
자리의 다른 모양(다른 숫자, 선, 상자), 두 PDF 중 한쪽에서 너무 흐려 윤곽이 안 잡히는 낱말.

수치의 근거 (낱말과 차트가 함께 있는 모아 찍기 20장짜리 문서 하나. 모아 찍기 기준에 대해 후보의 짝
없는 낱말이 1257개다. 한 장에 한 쪽 기준(*한 장에 한 쪽 기준* 절)에 대해서는 표 칸 885개에 짝이 있고
차트 글자 371개가 모두 그려진 글자로 나온다):

- 885개는 기준 PDF 에 없는 표 칸이다. 한글이 메모 때문에 줄인 쪽 가운데 열 쪽에서 표의 오른쪽 열을
  그리지 않았다. 기준의 그 자리에는 잉크가 없고 885개 모두 짝 없는 낱말로 남는다.
- 371개는 다섯 쪽에 있는 차트 글자다. 기준 PDF 에는 그 차트가 그림으로 들어 있다. 315개가 그려진
  글자로 나온다 (117개 중 117, 105개 중 103, 41개 중 41, 36개 중 35, 72개 중 19). 나머지 중 53개는 짝지은 낱말이 쪽 번호 세 낱말뿐인
  쪽에 있다. 그 세 낱말로 만든 맞춤은 쪽 위쪽에서 2pt 넘게 어긋난다 (다른 쪽들의 축척을 쓰면
  72개가 모두 그려진 글자로 나온다). 2개는 방사형 차트 한가운데의 `0` 이고(4단계), 1개는 기준에서만
  굵게 그려져 있다(1.6%).
- 1개는 표 안의 숫자다. 기준에는 Type 3 글꼴의 글자로 있는데 `pdftotext` 가 낱말로 내지 않는다.
  그려진 글자로 나온다.
- 해상도와 0.25pt: 이 글자들은 기준에서 3.5pt 쯤이고, 1pt 에 4픽셀이면 숫자 하나가 8x10 픽셀이다.
  그림 쪽처럼 `-tol` 하나만 허용 오차로 쓰고 옮겨 보지 않으면, 240개 중 237개가 크기가 같은 *다른*
  글자의 기준 그림과도 겹쳤고 (`12` 자리의 `10`), 309개 중 279개는 자기 그림을 1.25pt 옮겨도
  겹쳤다. 옮겨 보면서 0.25pt 로 재면 1pt 에 4픽셀에서는 300개 중 264개를 찾고 231개 중 13개가 다른
  글자와 겹쳤다. 8픽셀에서는 300개 중 299개, 231개 중 5개였다. 0.125pt 로는 300개 중 93개만 찾았다.
  두 프로그램이 같은 글자를 똑같이 그리지 않기 때문이다 (한글은 글자를 경로로, 다른 크기로 쓴다).
- 찾은 자리에서 네 방향으로 1.5, 2, 3pt 씩 옮기면 316개 중 하나도 그려진 글자로 나오지 않는다
  (각각 1264번). 크기와 글자 수가 같은 가장 가까운 다른 글자의 기준 그림에 얹으면 245개 중 5개가
  나온다 (`26` 자리의 `28`, `2021년` 자리의 `2022년`, `1,000,000` 자리의 `2,000,000`).

### 판정

문서는 다음을 모두 만족하면 통과한다.

- 쪽 수가 같다.
- 짝지은 낱말이 다른 쪽 번호에 있지 않다.
- 짝 없는 낱말이 (양쪽 모두) 없다. 그림 쪽의 후보 낱말과 기준이 그림으로 그린 글자는 세지 않는다.
- 가장자리 최대 편차가 `-tol` 이하다.
- 그림 쪽마다 그림 차이가 `-ink` % 이하다.

한 장에 한 쪽 기준이 있는 문서는 쪽이 그 기준의 쪽이고, 후보의 장도 모아 찍기 기준과 같아야 한다.
장 수가 같고 크기가 `-tol` pt 안에서 같아야 한다.

`-reconvert` 를 주면, 한글로 인쇄한 후보 HWP/HWPX 도 기준 PDF 에 대해 같은 시험을 통과해야 한다.

판정에 넣지 않고 보여만 주는 것: 치환(`subst`), 맞춤 축척(모아 찍은 장의 두 반쪽 축척이 다른
것도), TXT 비교. TXT 는 빈 줄과 줄 끝 공백을
빼고 `&#NNNN;`(한글이 자기 코드 페이지 밖 글자를 이렇게 쓴다)을 풀어서 줄 단위로 비교한다. 두 변환기는
표와 공백을 텍스트로 옮기는 방식이 달라서 참고용이다.

보고서의 `## Differences` 에는 실패한 문서마다 편차가 가장 큰 낱말, 짝 없는 낱말의 앞 몇 개, 치환의
앞 몇 개를 적는다.

### 한계

- 세로 가운데는 글꼴 상자에서 나온다. 두 PDF 가 다른 글꼴로 그리면 기준선이 같아도 가운데가 움직인다.
  기준선은 Type 3 글꼴이 든 문서에서만 쓴다.
- 그림 비교는 글자가 아니라 모양을 본다. 차트 글자의 글꼴이 다르면 윤곽이 달라지고, 모양이 비슷한
  다른 글자는 잡히지 않는다. 색 범위의 4분의 1보다 흐린 경계(옅은 형광펜, 옅은 회색 선)는 재지 않는다.
- 그려진 글자를 찾는 것도 모양을 본다. 여러 글자 가운데 한 글자만 다른 낱말이 그려진 글자로 나올
  수 있고 (위의 245개 중 5개), 굵기만 다른 같은 글자도 그렇다. 3.5pt 글자에서 굵은 것과 보통 것의
  차이는 0.25pt 보다 작다. 글꼴이 다른 글자는 찾지 못한다. 다른 글꼴로 만든 후보에서는 위의 371개
  가운데 200개만 찾았다.
- 그려진 글자는 그 쪽의 맞춤이 옮겨 놓는 자리에서 찾고, 맞춤은 짝지은 낱말로 만든다. 낱말이 한 줄에
  몇 개뿐인 쪽은 그 낱말에서 먼 곳의 맞춤이 부정확해서 그곳의 그려진 글자를 찾지 못한다.
- 후보가 그림으로 그리고 기준에는 낱말로 있는 글자는 찾아보지 않는다. 그것은 짝 없는 기준 낱말이다.
- 한글은 문서의 인쇄 설정(예: 모아 찍기 2쪽)을 따른다. 따르지 않는 후보는 쪽 수가 달라지고, 한 장에
  한 쪽 기준이 있으면 장 수가 달라진다.
- 한 장에 한 쪽 기준은 인쇄 설정이 두 쪽 모아 찍기(`PrintMethod` 4)인 문서에만 만든다. `ref` 가 이것을
  알기 전에 만든 기준에는 없고, `ref` 를 다시 돌려야 생긴다.
- 한 장에 한 쪽 기준의 쪽과 비교하는 반쪽은 장 위에서 후보 pt 로 잰다. 거기서 쪽은 원래 크기의
  0.71 쯤이라, 장 위의 1pt 는 쪽에서 1.4pt 다. 한 장에 한 쪽으로 찍은 후보는 원래 크기로 잰다.
- 한 장에 한 쪽 기준에서 낱말이 없는 쪽은 맞춤이 없고, 맞춤 없이는 후보 장의 반쪽을 그 쪽에 얹을 수
  없다. 그런 쪽은 비교하지 못했다고 적고 문서는 실패한다.
- 한 장에 한 쪽 기준이 있으면 모아 찍기 기준과는 낱말을 비교하지 않는다. 그래서 후보가 반쪽을 장의
  어디에 놓았는지는 재지 않는다. 반쪽마다 자기 맞춤을 가진다.
- 모아 찍기인지는 낱말만 보고 가린다 (*모아 찍기* 절). 가로 용지에 세로 쪽 둘을 나란히 찍은
  것만 다룬다. 가운데 세로선에 걸친 낱말이 있거나 반쪽이 줄지 않은 모아 찍기 장은 한 쪽으로
  비교한다.
- 반쪽도 다른 쪽처럼 자기 맞춤을 가진다. 반쪽이 통째로 옮겨지거나 줄어든 것은 편차가 아니다.
